How Not to Build an AI Art Pipeline

Characters worked for my game. Objects needed animation, placement and scale, and every fix felt like duct tape.

11 November 2026

I am building a game that started out as digital D&D with an AI game master, and turned more into an AI writing and animating a comic book as you play it. Every character, object and location in a scene has to be thought of, generated, placed, and animated.

My first plan was to commission assets directly from an illustrator whenever the game has nothing fitting in store, so the game would have mailed a commission and checked what was uploaded. Then it sank in that a continuously running game that generated assets on the fly even with a bucket of already existing assets to choose from will quickly be impossible to be satisfied by even a group of illustrators and already with a few commissions it is financially not viable.

So just going for AI art seemed like the solution but it would lose the illustrator’s style and human involvement, so instead I thought to train a LoRA, a small add-on for an AI model, that learns a single art style from a commissioned dataset drawn to a spec, which the illustrator delivers through the same validation workflow. Now the game can generate as many assets as it needs, in that style, at a fraction of the cost of commissioning each one, and the artist earns royalties each time an asset is used.

That dataset is still a todo since commissioning it will be expensive, so everything in this post runs on a rudimentary set, as I decided to build the infrastructure first without worrying about art quality too much.

Characters

For characters the pipeline runs like this: Using the trained LoRA the model draws a portrait and a standing figure from a prompt on white, animation frames are derived from those two bases by prompting for an arm on the hip etc., and every frame is rendered again on black so I can solve its transparency from the difference.

All this worked quite well. Every single character gets the same set of frames and the game puts them in fixed spots over the scene.

Next up are objects, things in the scene you can tap, and initially I thought of them as an extension of this. Once I started adjusting the workflow, it felt the other way around. Objects seem to need all the tough parts that characters never had to deal with:

  • whatever the object is, it has to be animated
  • each is to be picked up and moved without the need to redraw a location
  • and an object must sit in a scene at the right size and ‘disappear’ in the backdrop

Object animation

Characters sit on one idle image, and the game has single action frames to swap in now and then. A bonfire has no idle state and therefore must cycle through frames constantly. Prompting became the problem two distinct motions have to be thought of so the model can follow it e.g. “flames leaning right” followed by “flames leaning left”, but it looked very unnatural when played in a loop as the model overdid it every time.

So I stopped describing the motion. Instead three bonfires are generated from the same prompt with different seeds, an LLM with vision points at the part that is meant to animate by outputting pixel coordinates, and a mask locks the rest of the image. Once all three cycle the mask lets only the flames through, which gives natural looking motion for cycling effects.

With animation working, the next step is to place the objects. In addition to the previously mentioned requirements, an object must also pick up the surroundings’ lighting and cast shadows, and potentially stand on other objects.

Composition

All of that could come from the scene itself as long as the objects were to be generated inside of it but the model started repainting the scene more than generating a proper object and trying to animate it just made the location flicker so I scrapped this approach.

Back to drawing on white, which left shadows, lighting and objects on objects open. The object also has got to match the scale the background is drawn at which changes with depth.

To solve size I gave each object a class, with a candle being tiny at 50 pixels, a torch small at 100, and a bonfire medium at 150, with large and huge being options as well. Also a location gets split into three planes, foreground, middle and background. An LLM sees the location and paints three colored areas over it. Therefore an object’s size is the object’s class times the plane’s factor of 1, 0.75 or 0.5, so a small torch at 100 pixels stands at 75 in the middle plane, and the drawing gets scaled to that.

Then the colored location gets passed with the object next to it as reference to an LLM which once again points at a pixel for the object to be placed and the color of the plane at that spot dictates the size at which the object is painted.

The whole thing end to end

When I ran everything together as a workflow with no human in the loop I got my wake-up call:

  • object animation only works for effects like fire or smoke
  • composition puts objects in spots that make little sense
  • an object’s scale does not fit the scene around it once size was solved and that is the biggest issue

Scale

On white the object fills the canvas it is generated on at about 512 pixels. Then we scale it down during composition to let’s say 100 pixels, and now despite being at the right size, the perceived scale of it is completely off because it does not match the art style anymore. In my example it is visible best when looking at the line width of the outlines which once an object was composited were far thinner than the lines in the image of the location.

To try to force a size and get the scale correct during generation I made the initial canvas as small as the object should be when placed, so the model would have no room to draw it any bigger. Sadly a canvas below 512 pixels made the model collapse completely. A chicken turns nearly realistic, despite the LoRA still being on, and a candle completely swaps its body instead of just the flame, so the animation system fell apart.

If we can’t go smaller with the canvas, my plan to fix it was to increase the size of the location image which should result in thinner lines when scaled down and I can use the minimum canvas for my smallest objects. However the location’s lines grew with its size while the objects’ lines stayed the same on any canvas.

Another approach to get scale right was to generate an object at normal size, scale it down to the size it is meant to be placed at and let the model redraw from this on big canvas, but the line weight was copied rather than redrawn.

Thoughts

Every step so far felt more like patching something with duct tape rather than solving issues and moving forwards. Rendering twice for transparency, repainting behind a mask for animation, shrinking and redrawing for scale.

What actually works:

  • character animations are great
  • generating objects on white in a style from a rudimentary LoRA came out right
  • a vision model pointing at an image by outputting pixels is a nice tool
  • fire and smoke animate well (at the cost of all other objects)
  • solving alpha from white and black gives very clean transparency (at the cost of generating everything twice)

But the main issue of perceived scale during object composition remains unsolved.

Pivot

So I thought to pivot to pixel art. Because pixels can be counted I thought it would help with scaling, as assets would be generated and then scaled up and down to exactly the right size, while also lighting and shadows might get a little easier, as a shadow in pixel art can just be a few darker pixels under the object and relighting pixels should be easier to get to look right than crisp pictures.

This move to pixel art would once again be more of a workaround rather than a real fix, as I am just looking to simplify away the problem of scale. Would pixel art hold up at all? Is simplifying the problems away the right path here, or are there just far simpler existing options to solve all of it more efficiently?

How Would You Do It?

How to composite AI art at all? It means choosing a spot, keeping each object separate from the scene so it can be picked up, sizing it for its place in the backdrop, making it look drawn into the scene by adding light and shadow, and resting it on other objects. Again, for me the problem with all of this was scale, so what approaches already exist to handle this properly?

Forcing the model to draw small, so the lines would match once scaled up and redrawn, was my way of solving it, but why does a model collapse on small canvases? My best guess is that neither the LoRA nor the base model ever trained on small images. Do other models or methods get around it?

Would it be worth going back to drawing objects in the scene and keeping a detached version for the inventory, at the cost of redrawing part of the location every time an object gets picked up?

My animation system with idle poses from characters might translate to pixel art, but how to handle animating things that cycle constantly?

If you are building something like this, what are you doing differently, what existing tools should I check out, and do you think pixels will solve scale?
